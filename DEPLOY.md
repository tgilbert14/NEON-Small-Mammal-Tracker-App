## Option A — Posit Connect Cloud (current git-backed target)

Connect Cloud deploys an R app straight from a public GitHub repo using `manifest.json`
(already generated by [`scripts/write_manifest.R`](scripts/write_manifest.R)).

The manifest is **lean and bundle-only**: it lists `global/ui/server.R`, `R/`, `www/`, the
precomputed `data/*.rds` indexes, the `data/sites/*.rds` bundles, and the demo sample — and
**91 runtime dependencies, NOT `neonUtilities` or `arrow`.** Ordinary packages resolve from the
dated Posit jammy snapshot; eight geospatial packages resolve from exact CRAN tarballs.
`neonUtilities` is referenced by a
*computed* name in `global.R` (`.NEON_PKG`) precisely so the dependency scanner never pins it:
it has no wasm build (would block a future shinylive export) and a live NEON pull on a cold
free-tier worker is a hang risk. The deployed app runs **entirely from the bundled `.rds`
files**; the optional live-fetch toggle only appears where `neonUtilities` is actually
installed (local dev). Force bundle-only anywhere with `SMT_LIVE=0`.

1. Sign in at <https://connect.posit.cloud> with GitHub.
2. **New Content → Shiny → from Git**, pick `tgilbert14/NEON-Small-Mammal-Tracker-App`,
   branch `main`. Connect reads `manifest.json` (`appmode: shiny`) and auto-detects the
   multi-file Shiny app (`global.R` + `ui.R` + `server.R`) — there is no single "primary
   file" to choose for a `ui.R`/`server.R` app; `global.R` is sourced automatically.
3. It reads `manifest.json`, restores packages, and serves. A reviewed merge updates the source
   revision available to Connect; confirm **Last deployed** and use **Republish** when it lags.
   Refresh automation itself never writes to `main`, and a merge is not a deployment receipt.
4. Copy the published URL → update the direct CTA `href` and structured `url` in
   `docs/index.html` (and the README status).

Regenerate the manifest whenever runtime dependencies change:
```r
# Pinned R 4.5.2 CI/refresh runtime with the declared geospatial closure:
Rscript scripts/write_manifest.R     # writes manifest.json + self-checks neonUtilities is absent
```

**Cold start:** the free tier sleeps. The landing page makes no unsolicited pre-warm request; the
worker begins waking only after the visitor follows the CTA. Availability is established only by
the semantic post-deploy workflow, never by an opaque network response.

## Option B — Shinylive / WebAssembly (best long-term: static, zero server)

Because the deployed app has **no hard runtime dependency on `neonUtilities`** (read-only bundled
`.rds`), it is a shinylive candidate — it could serve from GitHub Pages alongside the landing
page. **Gate: every package needs a wasm binary.** Check each at <https://repo.r-wasm.org/>
before committing — most importantly **`leaflet`** (the picker map), plus `shiny, bslib, bsicons,
plotly, DT, dplyr, tidyr, stringr, RColorBrewer, shinyjs, shinycssloaders, htmltools`. These are
mainstream, but **verify per-package — one missing binary kills the static build.** Also weigh
the **bundle size**: 46 site `.rds` + the indexes ship to the browser, so confirm the wasm
payload is acceptable.

```r
# install.packages("shinylive")
shinylive::export(".", "docs/app")   # emits a static site under docs/app/
# then point the landing CTA at "app/" and you have ONE GitHub-Pages deploy: landing + app
```

If the wasm + size check is clean, this is the cheapest home and removes Connect Cloud's cold
start. If anything fails, stay on Connect Cloud (Option A).

## Retire the old target

Once Connect Cloud (or shinylive) is live and the landing page points at it:
- In your **shinyapps.io dashboard**, archive/delete the `RatTrapHistory` application (this is a
  dashboard action — it is not done from this repo).
- Then delete the inert `rsconnect/shinyapps.io/` tree from the repo (`deployApp()` /
  `scripts/deploy.R` is no longer the path; `scripts/write_manifest.R` + git is).
